### 1.2 目标与非目标

**目标**

1. 消灭「用户什么都没填，数据库已存在一条空草稿」的脏数据（问题汇总第 2 条的源头）。
2. 图片不再依赖提前拿到的 `order_id`，未完成的工单不在服务端留下任何痕迹。
3. 减少新建报修的点击次数与等待（进入编辑页不再有「创建中…」loading）。
4. 修复故障描述区导致整页无法滚动的问题。

**非目标（本次不做）**

- 不做草稿的多设备同步。
- 不改变工单状态机与审核流程（`draft → reported → …` 保持不变）。
- 不改动业务员完工登记、收据、导出等既有功能。
- Web 管理后台不涉及（后台不提供建单入口）。

### 1.3 已确认的关键决策（2026-09-30 与甲方确认）

| 编号 | 决策项 | 结论 |
|---|---|---|
| D1 | 草稿主方案 | **A1 本地优先**：新建不发请求，首次保存/提交时才落库分配 ID |
| D2 | 图片上传时机 | **B1 建单后批量上传**：选图先入本地队列，拿到 `order_id` 后串行上传 |

| D4 | 未保存退出行为 | **自动存本地，回来可续填**：不弹三按钮、不落服务端、下次新建自动恢复 |

## 第二章 现状分析

### 2.1 现有链路（改造前）

```
① list.vue 点「+新建」
     └─ POST /orders {} ─────────────► 服务端立即建空草稿 + timeline(create_draft)
                                        返回 order_id
② navigateTo edit?id={order_id}
③ edit.vue init：GET /orders/options + GET /orders/{id}（回填）
④ 用户边填边（手动）保存 ─ PUT /orders/{id}
⑤ 选中图片即刻上传 ───── POST /orders/{id}/images（每张独立请求）
⑥ 提交：PUT 全量 → POST /orders/{id}/submit → 订阅消息授权
⑦ 放弃：DELETE /orders/{id} → 工单状态置 cancelled（**软删除，记录仍在**）
```

### 2.2 涉及代码位置

| 环节 | 位置 | 说明 |
|---|---|---|
| 建单入口 | `uni-app-frontend/pages/order/list.vue:263 createOrder()` | 先 `POST /orders` 再跳转 |
| 后端创建 | `backend/internal/service/order.go:350 Create()` | 建空行 + `create_draft` 时间轴 |
| 草稿上限 | `order.go:36 maxDraftCount = 5` | 超限返回 `ErrDraftLimit` |
| 后端更新 | `order.go:391 Update()` | 指针字段局部更新 |
| 删除 | `order.go:559 Delete()` | 仅置 `cancelled`，图片软删，**非物理删除** |
| 图片上传 | `pages/order/edit.vue:454 uploadFiles()` | 依赖 `this.orderId`，选中即传 |
| 提交校验 | `order.go:848 validateSubmitFields()` | 图片**非必填** |
| 拦截返回 | `edit.vue:171 <page-container :show="true">` | 常驻显示，用于拦截左上角返回 |

### 2.3 主要问题

1. **空草稿落库**：点「+新建」瞬间就有 DB 记录，哪怕立刻退出。丢弃后也只是 `cancelled`，永远占位。
2. **图片强制即时上传**：`uploadOrderImage(orderId)` 必须要有 ID，导致图片逻辑无法延后。
3. **进入编辑页有等待**：需等一次网络往返，期间显示「创建中…」。
4. **整页无法滚动（问题 4）**：见 4.2，需先复现定位，首要怀疑对象是常驻的 `page-container`。
5. **表单默认值缺失**：报修单位只在「仅 1 个可选单位」时才自动选；联系人/电话恒空。
6. **设备类型与问题类别需两次 picker 点击**，且微信原生 `<picker>` **不支持代码触发弹出**。

## 第三章 总体方案：本地优先 + 延迟分配 ID

### 3.1 方案概述

新建工单时**不在服务端创建任何记录**，整张表单（含图片）先落在小程序本地；只有当用户显式点击「保存草稿」或「提交报修」时，才向服务端 `POST /orders` 携带内容一次性建单、拿到 `order_id`，随后再批量上传图片。

编辑**已存在的服务端草稿**（列表页点草稿卡片进入，`?id=xxx`）时行为保持现状：`GET /orders/{id}` 回填、`PUT /orders/{id}` 保存、图片即时上传。两条路径在同一页面共存，用 `this.orderId` 是否为空区分。

### 3.2 两种进入模式

| 模式 | 触发 | 标识 | 数据来源 | 保存动作 |
|---|---|---|---|---|
| 新建 | 列表页「+新建」 | `orderId === ''` | 本地草稿（storage）或默认值 | `POST /orders`（带内容）→ 得 ID → 传图 |
| 编辑已有 | 列表页/详情页点已有草稿 | `orderId` 非空 | `GET /orders/{id}` | `PUT /orders/{id}`（图片即时上传） |

### 3.3 时序

**新建 → 保存草稿**

```
点击「+新建」
  → 立即 navigateTo('/pages/order/edit')（无 id，无网络等待）
  → onLoad：本地若有未完成的草稿 → 顶部提示「继续上次未完成的报修 · 放弃」
     选「继续」→ 恢复本地内容；选「放弃」→ 清除并按默认值初始化
  → 初始化默认值（见 4.3 / 4.4），此后 captureSnapshot()
  → 用户编辑：表单变化 500ms 防抖 → 写入本地 storage（含图片本地路径）
  → 点「保存草稿」
      ├─ POST /orders { enterprise_id, category_id, property_id, description, urgency, room, contact }
      │       （服务端仍在草稿上限内才会成功，见 3.8）
      ├─ 得 order_id → this.orderId = order_id
      ├─ 串行上传本地图片队列：POST /orders/{id}/images × N（失败保留队列）
      └─ toast「已保存草稿」，清本地草稿
```

**新建 → 提交报修**

```
点「提交报修」
  → 本地表单校验（validateForm，保持不变）
  → wx.requestSubscribeMessage（三个模板，保持不变）
  → POST /orders（带内容）→ 传图 → POST /orders/{id}/submit
  → 成功：写入位置记忆（4.4）、清本地草稿、navigateBack
```

### 3.4 本地草稿数据结构与存储

新增 `uni-app-frontend/utils/localDraft.ts`：

```typescript
/** 本地待上传图片项 */
export interface LocalDraftImage {
  /** 本地持久文件路径（savedFilePath），跨会话可用 */
  path: string
  /** 可直接用于 image src 的预览路径 */
  preview: string
  name: string
  size: number
  /** 上传成功后的图床 URL（未上传为空） */
  url?: string
}

/** 本地草稿（仅保留最近 1 份） */
export interface LocalDraft {
  /** 结构版本号，用于升级兼容 */
  v: 1
  localId: string
  updatedAt: number
  form: {
    enterprise_id: string
    category_id: string
    property_id: string
    description: string
    urgency: string
    room: string
    contact_name: string
    contact_phone: string
  }
  images: LocalDraftImage[]
  /** 已落库时回填，用于区分「纯本地」与「已同步」 */
  orderId?: string
}
```

| 约定 | 取值 |
|---|---|
| storage key | `xn_localDraft_{userId}`（单份，覆盖写） |
| 容量 | 图片 ≤9 张，与服务端 `maxFaultImages = 9` 对齐 |
| 图片持久化 | `uni.saveFile` 到 `wx.env.USER_DATA_PATH/xn_draft_imgs/`，保存前清空旧目录 |
| 过期 | `updatedAt` 超过 **7 天**自动丢弃 |
| 读写时机 | 编辑中 500ms 防抖写入；`onUnload` 立即写一次（兜底强杀） |
| 清理时机 | 保存草稿成功 / 提交成功 / 用户点「放弃」/ 过期 |

### 3.5 ID 分配时机

**唯一分配点：首次需要服务端实体时**（保存草稿、提交报修）。在此之前界面上不存在任何 `order_id`，「新建」操作零服务端副作用。

带来的收益：

- 服务端草稿数与实际用户意图一致，`maxDraftCount = 5` 不再被空草稿占用。
- 直接命中问题汇总第 2 条——不再依赖「删除」来清理垃圾数据。

### 3.6 图片逻辑：批量延迟上传（决策 D2）

| 场景 | 行为 |
|---|---|
| 新建（无 ID） | 选图后**只入本地队列**：显示本地缩略图、`uni.saveFile` 落盘；**不发任何网络请求** |
| 新建 → 保存/提交后 | 拿到 ID 后**串行**（concurrency = 1）逐个 `POST /orders/{id}/images`，显示「正在上传第 x/N 张」 |
| 编辑已有草稿（有 ID） | 维持现状即时上传，选中即传，无需改 |
| 单张失败 | 中断剩余上传 ≠ 全失败；失败项保留 URL 为空，toast「n 张上传失败，可在草稿中重试」，工单本身仍已保存 |
| 重试入口 | 图片右下角显示「重试」角标，点击进入上传队列重试 |
| 删除已入队图片 | 纯本地移除；若已上传（有 `url`）且工单已落库，则通过 `PUT /orders/{id}` 的 `images` 全量替换移除 |

> 说明：`POST /orders/{id}/images` 接口本身**不作改动**（multipart 与 base64 两种形式均已支持），只是调用时机从「选中时」变为「拿到 ID 后」。

### 3.7 退出与删除行为（决策 D4）

| 状态 | 返回/左上角返回时 | 「删除」按钮 |
|---|---|---|
| 新建且未落库 | **不弹窗**，内容自动落本地，直接返回 | 仅清本地草稿 + 返回（不调后端） |
| 编辑已有服务端草稿 | 保留现有「保存 / 不保存 / 取消」三按钮弹窗 | 现状不变（`DELETE /orders/{id}` + 清本地） |

由此，原来的 `page-container` 拦截机制**可以移除**（见 4.2），因为它存在的主要目的是防止「未保存就丢失」，而现在本地已自动兜底。

### 3.8 兼容与降级

| 情况 | 处理 |
|---|---|
| 服务端草稿已达 5 份 | 保存时后端返回 `ErrDraftLimit`；前端 toast「草稿最多保留 5 份，请先处理已有草稿」，**本地草稿不清除**，用户可先去列表清理再回来保存 |
| 旧版本小程序 | 仍以空 body 调用 `POST /orders` → 后端保持空 body 的老行为，不受影响 |
| 用户禁用存储 / 存储写失败 | 降级为「仅内存暂存」，页面内正常编辑，`onUnload` 时提示「本地保存失败，请手动保存草稿」 |
| `uni.saveFile` 不可用 | 退回临时路径，提示用户本次会话内完成保存 |
| 多设备 | 明确不同步；新建页只恢复本设备的本地草稿 |

## 第四章 UI 改造细则（问题 3-8）

### 4.1 设备类型 → 问题类别两级联动（问题 3）

**约束**：微信原生 `<picker>` 无法用代码触发弹出，所以改造必须换容器。

**方案：底部弹层两级选择（推荐）**

```
点「设备类型」cell
  └─ 打开 wd-popup（position="bottom"，高度 ~60vh）
       左侧 scroll-view：项目大类列表
       右侧 scroll-view：当前大类的属性列表
       选中左侧大类 → 右侧自动刷新列表（默认选中第一项并高亮）
       点击右侧属性 → 立即回填 category_id + property_id，关闭弹层
       该大类无属性 → 右侧显示空态文案，允许只选大类后关闭
  └─ 再次打开时自动定位并滚动到当前大类/属性
```

- 数据源复用现有的 `GET /orders/options`（`categories[].properties[]` 已包含），**接口不变**。
- 弹层顶部保留「取消 / 确定」：点确定时若只选了大类未选属性，提示「请选择问题类别」。
- 备选方案：wot-design-uni `wd-picker` 两级联动（样式统一但弹层定制性差）；不采用 `wx.showActionSheet`（上限 6 项且不可滚动）。

### 4.2 故障描述区：滚动修复 + 清空键（问题 4、5）

**关于问题 4：这是本次唯一需要先复现定位的缺陷。** 页面样式与 `pages.json` 均未设置 `disableScroll`，`.page` 也无滚动限制，因此按可能性排序给出三个候选根因；修复以 D-1 为主，若验证不成立再依次下探。

| 候选 | 根因假设 | 验证方法 |
|---|---|---|
| **D-1（首要怀疑）** | `edit.vue:171` 常驻 `<page-container :show="true">` 形成覆盖层，吃掉页面触摸滚动；内容不满一屏时症状不可见，常见问题 chips 撑高页面后暴露 | 临时把 `containerShow` 初始值改为 `false` 后真机验证：能滚动即确诊 |
| D-2 | 键盘弹出时 `adjust-position` 上推页面，固定 footer 与原生 textarea 错位导致按钮点不到 | 描述框失焦后再尝试滚动/点击；对比设置 `adjust-position="false"` |
| D-3 | 原生 `textarea` 层级问题，或 `wd-popup` 关闭后残留 `lock-scroll` 遮罩 | 临时将 textarea 换成多行 `input` 对比；检查弹窗关闭后的 `overflow` |

**主修复动作**

1. 移除常驻 `page-container`，改用微信原生 `wx.enableAlertBeforeUnload({ message })` 拦截左上角返回（原生弹窗，无覆盖层、不影响页面滚动）；页面 `onUnload` 时 `wx.disableAlertBeforeUnload()`。不支持该 API 的低版本基础库直接降级为「不拦截」（已有本地暂存兜底）。
2. 常见问题 chips 区：`max-height: 220rpx` + 内部 `scroll-view` 滚动，并加「展开/收起」，避免撑爆页面。
3. `.page` 底部 `padding-bottom` 由 `160rpx` 增至 `220rpx`，保证三按钮 footer 不遮挡内容。
4. footer `z-index` 提升，确保在原生组件之上可见可点。

**清空按键（问题 5）**

- **形态（2026-09-30 定稿）**：底部与字数**同一行**的**文字按钮「清空」**，**红色**（`#e64340`）、**左对齐**描述框内边距（与框左边缘对齐），字数 `0/500` 靠右；**仅在有内容时显示**（无内容时该位置留空，字数仍靠右）。
  - 已废弃原「右上角浮动 × 圆标」方案：输入区图标易误触，且视觉上与字数分离。
- 点击直接清空（不做二次弹窗），并 toast「已清空」+ 3 秒内提供「撤销」入口（可选，P2）。
- 清空后 `description` 为空，不参与脏检查基线变更（快照机制不变）。

### 4.3 默认值与输入框快速清空（问题 6）

```typescript
// edit.vue：新建模式下的默认值初始化
const user = useUserStore().userInfo
const entStore = useEnterpriseStore()

// 报修单位：默认「我的企业」当前选中上下文
form.enterprise_id = entStore.currentEnterpriseId || ''
// 联系人 / 电话：默认报修人
form.contact_name = user?.nickname || ''
form.contact_phone = /^1\d{10}$/.test(user?.phone || '') ? user!.phone! : ''
// 位置：最近一次填写地点（见 4.4）
form.room = uni.getStorageSync(`xn_lastRoom_${user?.id}_${form.enterprise_id}`) || ''
```

- 初始化顺序：默认值填充 **→** `captureSnapshot()`，保证默认填充不计入「用户已改动」（与现有自动选单位的做法一致）。
- **输入框快速清空**：「位置 / 联系人 / 联系电话」三个 cell 在**有值或聚焦时**显示右侧清除图标，点击清空并重新聚焦该输入框。
- 报修单位为 picker，属必填项，不提供清除（占位文案「请选择单位」保持不变）。

### 4.4 位置记忆（问题 7）

> **决策（2026-09-30）**：采用**本地最近 N 条**方案，不建服务端表、不做企业位置字典。
> 选型依据：库内 1000+ 工单去重后仅 15 个位置、单企业实际在用 12 个，位置高度重复；
> 但本轮目标是「记住上一次填写的地点」，本地方案零后端零迁移即可满足，
> 服务端表（C）/ 企业字典（D）留作后续治理脏值（`娃儿安慰`、`位置`、`123`）时的升级路径。

| 项 | 约定 |
|---|---|
| storage key | `xn_roomHist_{userId}_{enterpriseId}`（按用户 + 单位维度隔离） |
| 数据结构 | `[{ room: string, ts: number }]`，按 `ts` 倒序，**trim 后精确去重**，上限 8 条 |
| 写入时机 | 保存草稿成功 **和** 提交报修成功时各写一次（`persistOrder()` 内统一调用 `rememberRoom()`） |
| 读取时机 | 新建模式初始化回填最近 1 条；编辑已有草稿时**不覆盖**数据库中已有的 `room` |
| 展示形态 | **仅保留聚焦浮层**（2026-09-30 定稿）：`@focus` 时弹出最多 8 条历史（对齐输入框、覆盖下方内容），**随输入实时过滤**；每条右侧 `×` 可单独删除。<br>~~常驻 chips~~ 已取消：占用纵向空间、破坏表单整体对齐美观 |
| 输入方式 | 始终允许手填，历史仅作快捷填充，不做强制字典约束 |

**实现要点（小程序端 blur 竞态）**：点候选时 `blur` 先于 `tap` 触发，故 `onRoomBlur` 延迟 250ms 再收起浮层；H5 端另用 `@mousedown.prevent` 兜底，避免 blur 抢先。

**对外接口**（`utils/localDraft.ts`）：`readRoomHistory` / `readLastRoom` / `pushRoomHistory` / `removeRoomHistory` / `clearRoomHistory` / `ROOM_HISTORY_MAX`。

### 4.5 多企业「切换单位」提示（问题 8，决策 D3）

- **触发条件**：`enterpriseOptions.length > 1`。
- **形态**：报修单位 cell 下方一行浅灰提示条
  `当前默认单位：{currentEnterpriseName()}，如需更换请点击「切换」`
- **点击「切换」**：`wx.showActionSheet` 列出全部 `approved` 单位 → 选中后

  2. 调用 `entStore.setCurrent(id)` **同步全局上下文**（后续新建默认使用新单位）；
  3. toast「已切换默认单位：XXX」；
  4. 按新单位重载位置历史 `xn_roomHist_{userId}_{newEnterpriseId}`，并回填该单位最近一次填写的地点。

## 第五章 后端接口变更

### 5.1 `POST /orders`（唯一变更点）

| 项 | 内容 |
|---|---|
| 现状 | 请求体为空，仅 count 校验 + 建空行 |
| 变更后 | 请求体**可选**，支持携带内容一次性建单 |
| 兼容性 | 空 body 行为完全不变（旧客户端不受影响） |

**入参（全部可选，字段与 `PUT /orders/{id}` 的 `UpdateOrderInput` 保持一致）：**

```go
// internal/service/order.go（新增，字段对齐 UpdateOrderInput）
type CreateOrderInput struct {
    EnterpriseID *string `json:"enterprise_id"`
    CategoryID   *string `json:"category_id"`
    PropertyID   *string `json:"property_id"`
    Description  *string `json:"description"`
    Urgency      *string `json:"urgency"`
    Room         *string `json:"room"`
    Contact      *string `json:"contact"`
}
```

> **不新增 `images` 入参。** 图片继续走 `POST /orders/{id}/images`，避免「图片先于工单落库」产生无归属记录，符合问题汇总第 2 条诉求。

**实现要点**

1. 把 `Update()` 中以指针字段赋值 + 校验的段落抽成 `applyDraftFields(order *model.RepairOrder, in UpdateOrderInput) error`，由 `Create` 与 `Update` **共用**，避免两套校验逻辑漂移。
2. `Create(ctx, userID, in)`：先验 `maxDraftCount = 5`（超限 `ErrDraftLimit`）→ 建行 → `applyDraftFields` → 保存 → 写 `create_draft` 时间轴。
3. 校验规则与 `Update` 完全一致：
   - `enterprise_id` 需已通过成员身份校验（`verifyMembership`）
   - `category_id` 必须有效；`property_id` 必须属于该类（大类变更时旧属性作废）
   - `description` 1-500、`room` 1-20、`contact` 0-40、`urgency ∈ {normal, urgent, very_urgent}`
   - 所有字段为「有值才校验、才写入」，指针为空表示不设值（保持可创建空草稿）
4. 响应体保持 `201 Created` + `{ order_id, status, created_at }`，**字段不变**。
5. handler 侧：`ShouldBindJSON` 需容忍空 body（监听 EOF 时按零值处理，不改变现有成功路径）。

### 5.2 不变更的接口

`GET /orders/options`、`GET /orders`、`GET /orders/{id}`、`PUT /orders/{id}`、`DELETE /orders/{id}`、`POST /orders/{id}/submit`、`POST /orders/{id}/cancel`、`POST /orders/{id}/images` **全部保持不变**。无需数据库迁移、无需新增 SQL。

## 第七章 异常与边界矩阵

| 场景 | 预期行为 |
|---|---|
| 新建未保存直接退出 | **不弹窗**，内容自动落本地；下次进入提示「继续上次未完成的报修 / 放弃」 |

| 保存/提交途中网络断开 | 本地草稿不被清除，用户可重试；服务端若已建单则下次按服务端草稿编辑（图片继续补传） |

| 本地图片文件被系统清理 | 预览失败显示占位图，点击可重新选择 |
| 提交成功后返回列表 | 清本地草稿 + 写位置记忆，列表 `onShow` 自动刷新 |
| 编辑已有草稿时新增图片 | 走原有即时上传（已有 ID），行为不变 |
| 用户未授权手机号导致 `userInfo.phone` 为空 | 电话留空不预填，用户手动输入（提交时仍校验 11 位手机号） |
