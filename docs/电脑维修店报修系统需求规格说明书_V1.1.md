## 第一章 引言

### 1.1 项目背景

目前在店内的报修流程管理上仍依赖电话沟通和微信聊天记录进行信息传递，存在以下突出问题：

- **漏单频发**：聊天消息淹没在群聊中，报修信息无统一入口，容易遗漏或遗忘。
- **责任扯皮**：缺乏明确的状态记录和时间戳，报修人与管理员对"谁说了什么、什么时候说的"各执一词。
- **效率低下**：报修人无法实时了解维修进度，需反复询问；管理员也难以批量管理和追踪工单。
- **数据沉淀缺失**：历史报修记录分散在多个聊天窗口中，无法检索、统计和导出，不利于运营分析。

基于以上痛点，本系统旨在将报修流程从线下沟通迁移至线上平台，实现**报修—接单—处理—完工—反馈**的全流程闭环管理。

### 1.2 项目目标

| 目标维度 | 具体描述 |
|----------|----------|
| **流程线上化** | 报修人通过公众号/小程序在线提交报修单，无需电话或微信沟通 |
| **状态透明化** | 工单状态实时可查，每一步操作留痕，形成完整时间轴 |
| **沟通成本最小化** | 关键节点自动推送通知，减少人工反复确认 |
| **数据可追溯** | 所有操作记录持久化存储，支持导出和审计 |

### 1.3 术语定义

| 术语 | 定义 |
|------|------|
| **工单（报修单）** | 报修人提交的一条维修请求记录，包含描述、图片、紧急程度等信息 |
| **草稿** | 报修人已填写但尚未提交的工单状态，可随时编辑和删除 |
| **已上报** | 工单已正式提交，进入管理员处理队列，报修人不可再修改 |
| **已阅** | 管理员已查看工单内容，确认收到报修请求 |
| **处理中** | 管理员已确认维修人员开始处理该工单 |
| **已处理** | 维修工作已完成，管理员可上传收据图片作为完工凭证 |
| **退回** | 管理员将工单退回报修人，工单状态回退为草稿，需填写退回原因 |
| **企业管理员** | 企业内拥有工单管理和成员管理权限的角色 |
| **普通报修人** | 企业内仅拥有提交报修和查看自己工单权限的角色 |
| **邀请码/二维码** | 企业创建后生成的唯一标识，用于成员加入企业的凭证 |
| **WebSocket** | 一种全双工通信协议，用于管理员后台实时接收新工单提醒 |

## 第三章 功能性需求

### 3.1 企业管理模块

#### 3.1.1 创建企业

- **功能描述** : 管理员在后台填写企业名称，系统自动生成唯一邀请码和对应二维码 
- **输入** : 企业名称（必填，2-50字符）, ... 
- **输出** : 动态二维码 
- **业务规则** :
  + 二维码内容为加入企业的链接，扫码后进入申请页面 

#### 3.1.2 加入企业

- **功能描述** : 用户扫描企业二维码，提交加入申请，管理员审核后生效
- **输入** : 邀请码（扫码自动填充）、用户昵称（取微信昵称）、手机号（选填）
- **输出** : 申请提交成功提示；管理员审核通过后用户成为企业成员
- **业务规则** :
  + 管理员可在后台开启"免审核"模式，用户扫码直接加入
  + 审核模式下，管理员可批量通过/拒绝
  + 一个用户可加入多个企业，切换企业后在对应企业下报修


#### 3.1.3 移除成员

- **功能描述** : 管理员可将成员从企业中移除
- **输入** : 选择目标成员 → 确认移除
- **输出** : 移除成功提示
- **业务规则** :
  + 移除后该成员不可再提交报修
  + 该成员的历史报修记录保留，不删除
  + 移除操作记录日志（操作人、操作时间、被移除人）


#### 3.1.4 成员列表管理

- **功能描述** : 管理员可查看企业内所有成员列表，支持搜索和筛选
- **输入** : 搜索关键词（昵称/手机号）
- **输出** : 成员列表（昵称、加入时间、报修数量、状态）
- **业务规则** :
  + 支持按加入时间、报修数量排序

---

### 3.2 报修工单模块

#### 3.2.1 新建工单 / 草稿

- **功能描述** : 报修人填写报修信息，可选择保存为草稿或直接提交
- **输入** : 报修项目名称（文本，必填，不超过20字）、报修描述（文本，必填，不超过500字）、故障图片（选填，最多9张，jpg/png，单张≤5MB）、
- **输出** : 草稿保存成功，工单状态为"草稿"
- **业务规则** :
  + 草稿可多次编辑、可删除

#### 3.2.2 提交上报

- **功能描述** : 报修人将草稿工单正式提交，工单进入管理员处理队列
- **输入** : 草稿工单ID
- **输出** : 工单状态变更为"已上报"；触发管理员端实时提醒
- **业务规则** :
  + 提交前校验必填项（描述、）
  + 提交后报修人不可修改工单内容
  + 提交时记录提交时间戳

#### 3.2.3 查看工单列表（用户端）

- **功能描述** : 报修人查看自己提交的所有工单列表
- **输入** : 状态筛选（全部/草稿/已上报/已阅/处理中/已处理/已退回）
- **输出** : 工单列表（工单号、描述摘要、状态、提交时间）
- **业务规则** :
  + 仅展示当前用户提交的工单，不展示他人工单

#### 3.2.4 查看工单详情（用户端）

- **功能描述** : 报修人查看单个工单的完整信息及处理时间轴
- **输入** : 工单ID
- **输出** : 工单完整信息 + 操作时间轴日志
- **业务规则** :
  + 时间轴记录所有状态变更（操作人、操作时间、操作类型、备注）

### 3.3 工单处理模块（管理后台）

#### 3.3.1 工单列表

- **功能描述** : 管理员后台展示企业内所有报修工单，支持多维度筛选和排序
- **输入** : 筛选条件（状态、紧急程度、时间范围、报修人）
- **输出** : 工单列表（工单号、报修人、描述摘要、状态、提交时间）
- **业务规则** :
  + 默认按提交时间倒序排列
  + 紧急工单在列表中高亮标识
  + 支持分页，每页20条


#### 3.3.2 状态流转

工单状态流转规则如下表所示：

| 当前状态 | 可执行操作 | 目标状态 | 触发条件 / 约束 |
|----------|-----------|----------|-----------------|
| 草稿 | 提交 | 已上报 | 表单必填项（描述）全部完成 |
| 已上报 | 查阅 | 已阅 | 管理员点击"我已看到"按钮 |
| 已阅 | 接单维修 | 处理中 | 管理员确认维修人员已上手 |
| 处理中 | 完工 | 已处理 | 管理员确认维修完成，可同时上传收据图片 |
| 任意非草稿状态 | 退回 | 草稿 | 必须填写退回原因（不少于10字） |

**状态流转约束：**

- 每次状态变更均记录操作日志（操作人、操作时间、原状态、目标状态、备注）。
- "退回"操作仅企业管理员可执行。
- "退回"后工单回到草稿状态，报修人可修改后重新提交。
- 状态流转不支持跳级（如"已上报"不能直接变为"已处理"）。

**状态流转图（文字版）：**

```
┌──────┐  提交   ┌──────┐  查阅   ┌──────┐  接单   ┌──────┐  完工   ┌──────┐
│ 草稿 │ ──────→ │ 已上报│ ──────→ │ 已阅 │ ──────→ │处理中│ ──────→ │已处理│
└──────┘         └──────┘         └──────┘         └──────┘         └──────┘
    ↑               │                │                │
    │    退回       │    退回        │    退回        │    退回
    └───────────────┴────────────────┴────────────────┘
                （退回需填写退回原因）
```

#### 3.3.3 工单详情（管理后台）

- **功能描述** : 管理员查看工单完整信息，执行状态流转操作
- **输入** : 工单ID
- **输出** : 工单完整信息 + 操作时间轴 + 操作按钮区
- **业务规则** :
  + 操作按钮根据当前状态动态展示（如"已上报"状态展示"查阅"和"退回"按钮）

#### 3.3.4 上传收据

- **功能描述** : 管理员在"完工"操作时可上传收据图片
- **输入** : 收据图片（1-3张，jpg/png，单张不超过5MB）
- **输出** : 收据图片关联至工单，报修人可在工单详情中查看
- **业务规则** :
  + 收据图片在完工后仍可补充上传
  + 已上传的收据图片可替换但不可删除

#### 3.3.5 工单导出

- **功能描述** : 管理员可将工单列表导出为Excel文件
- **输入** : 导出范围（全部 / 按筛选条件 / 按时间范围）
- **输出** : Excel文件（.xlsx），包含工单号、报修人、描述、状态、提交时间、完工时间等字段

### 3.4 消息通知模块

#### 3.4.1 用户端通知（公众号模板消息）

- **功能描述** : 工单状态变更时，通过微信公众号模板消息通知报修人
- **触发条件** : 工单状态变为"处理中"、"已处理"、"退回"时触发
- **通知内容** : 工单号、状态变更描述、变更时间、查看详情链接
- **业务规则** :
  + 每次状态变更仅推送一次通知
  + 如用户未关注公众号，通知失败时记录日志，不阻断流程
  + 退回通知中包含退回原因

#### 3.4.2 管理员端通知（WebSocket实时推送）

- **功能描述** : 有新工单提交时，管理后台实时弹窗提醒
- **触发条件** :
  + 任意新工单提交时
- **通知内容** : 工单号、报修人、描述摘要、提交时间
- **业务规则** :
  + 管理员后台页面保持打开时通过WebSocket实时推送
  + 管理员离线时通知不丢失，重新登录后在通知中心查看未读消息
  + 弹窗可手动关闭，5秒后自动消失
- **优先级** : P0

#### 3.4.3 管理员端通知（公众号模板消息）

- **功能描述** : 有新工单提交时，管理后台同时通过微信公众号模板消息通知管理员
- **通知内容** : 工单号、报修人、描述摘要、提交时间
- **业务规则** :
  + 对于每个新工单仅发送一条通知

## 第四章 非功能性需求

### 4.1 性能需求

| 指标 | 要求 | 说明 |
|------|------|------|
| 后台页面加载时间 | < 2秒 | 首次加载，不含图片上传等待 |
| 工单提交响应时间 | < 1秒 | 从点击提交到返回成功提示 |
| WebSocket消息推送延迟 | < 1秒 | 从工单提交到管理员收到弹窗 |
| 图片上传速度 | 单张5MB图片上传 < 5秒 | 依赖网络带宽，按4G以上网络评估 |
| 并发支持 | ≥ 10个用户同时操作 | 报修量不大，该指标留有余量 |

### 4.2 安全需求

| 安全项 | 要求 | 实现方式 |
|--------|------|----------|
| 管理员登录 | 微信扫码登录，不支持账号密码 | 调用微信网页授权OAuth2.0 |
| 数据隔离 | 不同企业数据物理/逻辑隔离 | 每条数据绑定企业ID，查询层强制过滤 |
| 接口鉴权 | 所有API需携带有效Token | JWT方式，Token有效期2小时，支持续期 |
| 图片上传安全 | 防止恶意文件上传 | 后端校验文件头Magic Number，限制MIME类型 |
| 操作审计 | 管理员关键操作记录日志 | 记录操作人、操作时间、操作类型、目标对象、IP地址 |
| HTTPS | 全站HTTPS | 使用Let's Encrypt免费证书或云服务商证书 |

### 4.3 可用性需求

| 指标 | 要求 | 说明 |
|------|------|------|
| 系统可用性 | ≥ 99.9% | 年度计划外停机不超过8.76小时 |
| 维护窗口 | 每周二 02:00-04:00 | 提前24小时通知 |
| 数据备份 | 数据库每日自动备份 | 保留最近30天备份，支持按日期恢复 |
| 灾难恢复 | RTO < 4小时，RPO < 24小时 | 故障后4小时内恢复服务，数据丢失不超过24小时 |

## 第六章 运行环境与交付物

### 6.1 运行环境

#### 服务器端

| 项目 | 要求 | 备注 |
|------|------|------|
| 操作系统 | Linux（CentOS 7+ / Ubuntu 20.04+） | 云服务器 |
| CPU | ≥ 2核 | 报修量不大，2核够用 |
| 内存 | ≥ 4GB | 含数据库 |
| 磁盘 | ≥ 50GB SSD | 含系统和图片存储 |
| 公网带宽 | ≥ 5Mbps | 图片上传需要带宽 |
| 域名 | 已备案域名 | 公众号配置要求 |
| 数据库 | PostgreSQL 13+ | 待定 |
| 运行时 | Go | 待定 |
| Web服务器 | Nginx | 反向代理 + 静态资源 |

#### 客户端

| 端 | 要求 |
|----|------|
