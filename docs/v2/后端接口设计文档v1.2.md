## 第一章 通用约定

### 1.1 认证方式

所有接口（除明确标注外）均需在请求头携带 JWT Token：

```
Authorization: Bearer <token>
```

- **Token 有效期**：2 小时
- **Token 刷新**：调用 `/auth/refresh` 获取新 Token
- **管理员接口** (`/admin/*`)：要求 JWT 中 `role>=1`（维修业务员或超级管理员）；涉及本单位成员审批/工单审核的接口另要求 membership.role=1（单位审核员），见各接口鉴权说明
- **超级管理员接口** (`/admin/users/*`)：要求 JWT 中 `role>=2`（仅超级管理员）
- **用户端接口**：要求已认证（`role>=0`），仅可操作自身数据
- **角色体系（双层模型）**：
  - 全局角色 `users.role`：0=普通用户 / 1=维修业务员（原"平台管理员"，店方）/ 2=超级管理员
  - 单位内成员身份 `memberships.role`：0=普通成员 / 1=单位审核员（成员审批 + 本单位 `reported` 工单审核[通过→pending_accept/退回] + 本单位工单查看与汇总）

| 全局值 | 角色 | 说明 |
|----|------|------|
| 0 | 普通用户 | 报修人，通过微信登录自动创建，须加入单位成为成员后提交工单，可管理自己的报修单 |
| 1 | 维修业务员（原平台管理员） | 店方维修工程师，处理业务范围内工单（接单/处理/完工/退回/重新打开/收据与费用登记），创建与管理单位；本版不再执行"查阅/已阅"动作 |
| 2 | 超级管理员 | 拥有维修业务员全部权限，额外可管理所有用户（查看/搜索/修改昵称/角色/手机号/重置密码）与项目字典 |

JWT Payload 结构：

```json
{
  "user_id": "uuid",
  "openid": "oXXXX",
  "role": 0,
  "nickname": "张三",
  "iat": 1753948800,
  "exp": 1753956000
}
```

#### 成功响应

```json
  "code": 0,
  "message": "success",
  "data": {},
  "request_id": "req_abc123"
}
```

```json
  "data": {
```

### 1.3 业务错误码

| 错误码段 | 含义 | 典型错误 |
|----------|------|----------|
| `0` | 成功 | — |
| `1000-1999` | 认证错误 | 未登录(1000)、Token无效(1001)、Token过期(1002)、微信授权失败(1010) |
| `2000-2999` | 权限错误 | 无权限(2000)、非管理员(2001)、无权操作该企业(2002) |
| `3000-3999` | 参数校验 | 参数无效(3000)、分页参数错误(3001)、图片格式/大小超限(3010)、图片数量超限(3011) |
| `4000-4999` | 资源不存在 | 通用(4000)、工单(4001)、用户(4002)、企业(4003)、成员(4004) |
| `4500-4599` | 业务规则冲突 | 工单不可修改(4500)、状态流转不合法(4501)、草稿必填不全(4502)、退回原因过短(4503)、重复操作(4504) |
| `5000-5999` | 服务端错误 | 内部错误(5000)、数据库错误(5001)、生成邀请码失败(5002) |
| `6000-6999` | 第三方服务 | 微信API失败(6000)、OSS上传失败(6001)、导出失败(6002) |

### 1.4 分页参数约定

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `page` | int | 1 | 页码，从 1 开始 |
| `page_size` | int | 20 | 每页条数，最大 100 |

### 1.5 时间格式

所有日期时间字段统一使用 ISO 8601 / RFC 3339 格式：

```
2026-07-31T14:30:25+08:00
```

### 2.4 管理后台密码登录

```
POST /auth/admin-login
```

> **说明**：管理后台使用「昵称 + 密码」登录。可登录人群：
> - 维修业务员（role=1）/ 超级管理员（role=2）
> - **单位审核员**（role=0 且在任一已通过单位中 membership.role=1）：此类账号本身为微信用户、默认无密码，需由超级管理员先经 6.4 设置登录密码后方可登录；
> 普通成员（role=0 且非单位审核员）无登录资格。

**请求体：**

```json
{
  "nickname": "admin",
  "password": "123456"
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `nickname` | string | 是 | 登录昵称，唯一 |
| `password` | string | 是 | 登录密码，bcrypt 存储，明文传输由 HTTPS 保证 |

**响应示例：** 同 2.1（`need_profile: false`；`user.role` 为 0/1/2，`user.enterprises[].role` 可为 `reviewer`/`member`）

**错误码**：
- `1011` 账号或密码错误（账号不存在 / 密码错误 / 未设置密码）
- `2001` 无权限（仅维修业务员/超级管理员或单位审核员可登录管理后台）


> **说明**：2.1 返回 `need_profile=true` 后调用。前端先上传头像（2.6），手机号支持**微信授权**与**手动输入**两种来源，将 `wx.login` 的 code 与手机号信息一并提交，后端创建用户并签发 JWT。

**请求体（手机号二选一）：**

```json
{
  "code": "021aXXGa1...",
  "nickname": "张三",
  "avatar_url": "https://cdn.example.com/avatar/xxx.png",
  "phone_code": "getPhoneNumber 返回的动态 code",
  "phone": "13800138000"
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `code` | string | 是 | 微信 `wx.login` 登录 code，换取 openid |
| `nickname` | string | 是 | 昵称，2-32 字符 |
| `avatar_url` | string | 否 | 头像 URL（经 2.6 上传获得） |
| `phone_code` | string | 二选一 | `getPhoneNumber` 授权返回的动态 code，后端解密手机号 |
| `phone` | string | 二选一 | 手动输入手机号，11 位、1 开头；`phone_code` 与 `phone` 同时传时以 `phone_code` 为准 |

**业务规则**：
- 同一 openid 已注册时，直接返回登录结果（幂等）
- 手机号唯一：已绑定的手机号返回错误
- 头像 URL 必须来自 2.6 上传接口

**错误码**：
- `3000` 手机号格式不正确 / 手机号与 phone_code 均未提供

**响应示例：** 同 2.1 已注册用户（`need_profile: false`）

### 5.17 本单位工单汇总统计（V1.3 C20 新增）

```
GET /admin/orders/stats
```

**鉴权**：单位审核员（role=0 + 对 `enterprise_id` 担任审核员）/ 维修业务员（role=1）/ 超级管理员（role=2）。

**用途**：支撑小程序「审核工单」页「统计」Tab 与未来 Web 汇总视图。实时聚合（每次请求按条件重新统计，无缓存）。

**查询参数**：

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| enterprise_id | string | 条件必填 | 统计单位范围。店方/超管：可选，不传 = 全部可见单位，传值 = 单单位；单位审核员：**必填**，且必须为其担任审核员的单位（跨单位返回无权限错误） |
| start | string | 否 | 起始时间（含），`YYYY-MM-DD` 或 RFC3339；与 `end` 均缺省 = **不按时间过滤（全部）**；「默认本月」由前端按快捷项换算后传入 |
| end | string | 否 | 结束时间（不含），同上 |

**统计口径**：
- 仅统计状态 ∈ 六种正式状态：`reported` / `pending_accept` / `processing` / `completed` / `cancelled` / `rejected`；**草稿（`draft`）不计入**（其 `submitted_at` 为空，自然被排除）。
- 分布区时间条件作用于 `submitted_at`（最新一次正式提交时间；草稿重提/已退回重提均会刷新该字段）；`today` 今日概况**不受 `start`/`end` 影响**。
- 范围条件作用于 `enterprise_id`；店方/超管不传时跨全部可见单位聚合。
- 已取消、已退回工单同样计入对应状态组，不因终态/退回而剔除。
- `today` 今日概况按**服务器本地日（0 点 ~ 次日 0 点）**统计：`pending_review` = 当前 `reported` 存量（无时间过滤）；`submitted_today` = `submitted_at` ∈ 今日（草稿不计）；`audited_today` / `rejected_today` = `order_timeline` 中 action 为 `audit` / `reject` 且 `created_at` ∈ 今日（JOIN `repair_orders` 限定企业域；审核员/店方操作均计）。

**响应 `data` 示例**：

```json

    "submitted_today": 3,
    "audited_today": 2,
    "rejected_today": 1
  },
  "total": 42,
  "range": { "start": "2026-09-01T00:00:00+08:00", "end": null },
  "by_status": [
    { "status": "processing", "label": "处理中", "count": 18 },
    { "status": "reported", "label": "已上报", "count": 5 }
  ],
  "by_category": [
    { "category_id": 1, "category_name": "网络", "count": 12 }
  ],
  "top_reporters": [
    { "user_id": 10, "nickname": "王五", "avatar_url": "https://cdn.example.com/a.png", "count": 8 }
  ],

```

| 字段 | 类型 | 说明 |
|------|------|------|
| today | object | 今日概况（独立于 `start`/`end`）：`pending_review`(int)=当前待审核存量 / `submitted_today`(int)=今日新增上报 / `audited_today`(int)=今日审核通过 / `rejected_today`(int)=今日退回 |

| range | object | 实际生效的时间范围（`start` 为 null 表示不限起始；`end` 为 null 表示统计到当前时刻） |
| by_status | array | 状态分布：**恒返回六种正式状态**（含 count=0），按 count 降序；`label` = 中文状态名（已上报/待接单/处理中/已处理/已取消/已退回） |
| by_category | array | 项目大类分布：按 `category_id` 归并（仅返回实际出现的类别），count 降序；`category_name` 取该类工单的名称快照（同名历史单合并在同一类别下） |
| top_reporters | array | 报修人排行：按**创建工单的用户**（`reporter`，昵称）分组，取 Top5（不足按实际），count 降序；含 `avatar_url`（用户头像，空串表示无，前端首字占位回退） |
| updated_at | string | 服务端聚合完成时间（RFC3339） |

**业务错误**：审核员对非本单位 `enterprise_id` 发起统计 → 返回无权限错误；`enterprise_id` 不存在 → 按 1.3 错误码返回资源不存在。

### 附录B：状态流转图

```
draft ──submit(必填校验)──→ reported ──audit(单位审核员)──→ pending_accept ──accept(维修业务员接单)──→ processing ──complete(登记费用+收据)──→ completed
   ↑ reject/取消             ↑ reject              ↑ reject                    ↑ reject              ↑ reopen(维修业务员)
   └──────────── rejected(已退回) ◀─────────────────────────────────────────────────────────────────────────┘
        (报修人修改后 submit 回 reported / 或 cancel 进 cancelled)

规则：
- reject（退回）原因≥10字，回 rejected（独立状态，与草稿区分）；已上报由单位审核员退回，待接单/处理中由维修业务员退回
- rejected 仅报修人可操作：修改后 submit 重新进入 reported，或 cancel 进入 cancelled
- cancel（取消）：仅报修人可在 draft/reported/pending_accept/rejected 发起，进入 cancelled（终态，列表底部单独展示）
- completed 可 reopen 回 processing 重新维修并重新登记完工信息；状态不支持跳级
```
