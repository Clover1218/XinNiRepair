## 第二章 经营范围模块（问题 10、28）

### 2.1 概念界定：为何不复用 `memberships`

| | `memberships` | `repairer_enterprises`（新增） |
|---|---|---|
| 语义 | 我**属于**这个单位 | 店方**授权**我服务这家客户 |
| 主体 | 普通用户 / 单位审核员 | 维修业务员 / 超级管理员 |
| 典型冲突 | 员工既是某单位成员、又是该单位的服务业务员时，一张表无法区分两种身份 | — |

两者看似同构，实则语义互斥。**混表会导致将来权限判定无法区分"他的报修身份"与"他的服务身份"**，故独立建表。

### 2.2 数据结构

`backend/migrations/013_repairer_scope.sql`：

```sql
-- 维修业务员经营范围：业务员 ↔ 可服务客户的指派关系
CREATE TABLE repairer_enterprises (
    id            UUID PRIMARY KEY,
    repairer_id   UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    enterprise_id UUID NOT NULL REFERENCES enterprises(id) ON DELETE CASCADE,
    status        VARCHAR(20) NOT NULL DEFAULT 'active',  -- active / revoked
    created_by    UUID REFERENCES users(id),              -- 指派人（超管）
    created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    revoked_at    TIMESTAMPTZ
);

CREATE UNIQUE INDEX uq_repairer_ent
    ON repairer_enterprises(repairer_id, enterprise_id);
CREATE INDEX idx_repairer_ent_ent
    ON repairer_enterprises(enterprise_id);
```

**设计取舍说明**

| 选择 | 理由 |
|---|---|
| 软撤销（`status` + `revoked_at`）而非物理删除 | 指派关系是有对账意义的商业边界。将来需要回答"这张单成交时他有没有权限"，物理删除会丢失证据。且软撤销不破坏唯一约束 |
| 复合唯一索引 `(repairer_id, enterprise_id)` | 正向查询（这个业务员能服务谁）由唯一索引本身覆盖；反向查询（这家客户由谁服务）走独立的 `enterprise_id` 索引 |
| 单主键 `id` 而非复合主键 | 与项目既有表风格一致（`memberships` / `audit_logs` 均为 UUID 单主键），便于将来独立引用某条指派记录 |

### 2.3 后端模块划分

```
backend/internal/
├── model/repairer_enterprise.go        # 结构体 + status 常量
├── repository/repairer_enterprise.go   # 数据访问
├── service/repairer_scope.go           # ★ 核心：可见范围计算
├── handler/admin_repairer.go           # 超管接口（注册于 cmd/server/main.go）
└── migrations/013_repairer_scope.sql
```

不改动任何现有 handler/service 的内部逻辑，仅通过 `access.go` 扩展点接入。

### 2.4 接口清单

全部挂在 `/api/v1/admin` 下并使用 **`RequireSuperAdmin`**（role=2）：

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/admin/repairers` | 业务员列表。**扩展现有实现**，每项增加 `scope_count` 字段 |
| `GET` | `/admin/repairers/:id/enterprises` | 某业务员的经营范围（页面初始化用） |
| `PUT` | `/admin/repairers/:id/enterprises` | **全量覆盖**指派，body `{enterprise_ids: []}` |
| `GET` | `/admin/enterprises/:id/repairers` | 反向查询：某客户企业由哪些业务员服务 |
| `GET` | `/admin/repairers/me/enterprises` | 业务员查询自身可见范围（小程序端筛选用） |

**关键取舍：`PUT` 全量覆盖，不做增量增删。**

后台页面做成多选 / 穿梭框，每次提交完整列表。增量接口需处理并发下的增删同步问题，全量覆盖天然幂等，且前后端状态易于保持一致。

### 2.5 权限注入点

**不新增中间件。** 差异在于"可见哪些企业"而非"能否进入该路由"——中间件只能拿到请求路径、拿不到业务数据范围，在中间件层解决不了这个问题。

唯一改动在 `service/access.go`（该文件头注释已预留此扩展点）：

```go
// VisibleEnterpriseIDs 返回该操作者可见的企业 ID 列表。
//   超级管理员 → nil（不限）
//   维修业务员 → 指派列表（无指派记录时返回空切片）
func (a *AccessService) VisibleEnterpriseIDs(ctx context.Context, op Operator) ([]string, error)

// AssertOrderVisible 校验单张工单是否对当前操作者可见（含已接单兜底）
func (a *AccessService) AssertOrderVisible(ctx context.Context, op Operator, o *model.RepairOrder) error
```

需注入的位置共 7 处（`internal/service/admin_order.go`）：

| 函数 | 行号 | 当前状态 |
|---|---|---|
| `ListOrders` | 191 | ✅ 已有部分判断，需改接入新接口 |
| `Stats` | 459 | ✅ 已有部分判断，需改接入新接口 |
| `StatsMetrics` | 531 | ❌ 完全无过滤 |
| `StatsRepairerOverview` | 592 | ❌ 完全无过滤 |
| `StatsByEnterprise` | 618 | ❌ 完全无过滤（**当前漏洞**） |
| `ListReporterOptions` | 347 | ❌ 完全无过滤 |

### 2.6 边界与降级规则

| 场景 | 规则 |
|---|---|
| 超级管理员 | 不受限制（`nil` 代表全量） |
| 维修业务员，有指派 | 仅可见指派范围内的企业数据 |
| 维修业务员，无指派 | **看不见任何企业**（D2） |
| 单位审核员 | 沿用现有"仅限本单位"逻辑，不参与范围计算 |

### 2.7 三个必做兜底（漏掉会出生产事故）

| 坑 | 后果 | 处理 |
|---|---|---|
| **已接单兜底** | 业务员接了 A 企业的单，超管随后把 A 移出其范围 → 该工单谁都看不见，**永久卡死在 `processing`** | `AssertOrderVisible` 追加规则：`repairer_id = op.UserID` 的工单**永远可见**，不受范围变化影响 |
| **存量兜底** | 采用 D2 后，上线瞬间现有业务员集体失明 | 迁移脚本末尾给所有 `role=1` 用户灌一遍现有全部企业，保证上线后行为与现状一致，之后由超管逐步收窄 |
| **接单前置校验** | 只挡查询不挡接单等于没做权限 | `Accept`（`admin_order.go:787`）增加范围校验，越界返回明确错误文案 |

## 第三章 状态机改造（问题 1、11 / 21、12、22）

### 3.1 现有状态机基线

`internal/model/model.go` L143-151：

```go
var ValidTransitions = map[OrderStatus][]OrderStatus{
    OrderDraft:         {OrderReported, OrderCancelled},
    OrderReported:      {OrderPendingAccept, OrderRejected, OrderCancelled},
    OrderPendingAccept: {OrderProcessing, OrderRejected, OrderCancelled},
    OrderProcessing:    {OrderCompleted, OrderRejected},
    OrderRejected:      {OrderReported, OrderCancelled},
    OrderCompleted:     {OrderProcessing},   // reopen
    OrderCancelled:     {},                  // 终态
}
```

> ⚠️ **文档订正**：`AGENTS.md` 第 6 节记载"reject 退回…回 draft，退回非独立状态"，与代码不符。
> **实际 `rejected` 是独立状态**，且 `rejected → reported`（重新提交）而非回 draft。
> 本文按代码现状推进，**建议同步修订 `AGENTS.md`**。

### 3.2 新增：撤回审核（问题 1、22）

需求"业务员未接单前，可去除已审核让申报人重新修改"对应一条不存在的逆向迁移：

```go
OrderPendingAccept: {OrderProcessing, OrderRejected, OrderCancelled, OrderReported},
//                                                                  ^^^^^^^^^^^^^^ 新增
```

新增动作常量：`ActionUnaudit ActionType = "unaudit"`

| 项 | 约定 |
|---|---|
| 前置条件 | 当前状态 `pending_accept` **且 `repairer_id` 为空**（尚未有人接单） |
| 执行动作 | 状态置 `reported`；清空 `audited_at` / `audited_by`；写 timeline `action=unaudit` |
| 权限 | 该单位单位审核员（`memberships.role=1`）或店方角色 |
| 通知 | 复用现有未接单提醒通道，通知报修人"审核已撤回，可修改后重新提交" |
| 幂等 | 已撤回（`reported`）状态下重复调用返回业务错误，而非静默成功 |

### 3.3 Tab 语义定义（问题 11 / 21）

"结束"→"已完成"为纯文案改名。"未完成"口径按 D3：

| Tab | 包含状态 | 说明 |
|---|---|---|
| **已完成** | `completed` | 不含 `cancelled` |
| **未完成** | `processing` + `pending_accept` | 已接手但未干完 |
| 待审核 | `reported` | 维持现有 |
| 已取消 | `cancelled` | 单独一栏，不属于"已完成"也不属于"未完成" |

实现建议：前端 Tab 不直接传单状态，改用**语义化 `tab` 参数**（如 `tab=unfinished`），由后端翻译成 `status` 列表。这样口径调整时只改后端一处，前后端不必同步发布。

小程序端（维修业务员 `pages/admin/order/list.vue`）与审核员端（`pages/review/index`）必须**用同一套口径**，否则会出现"两端数字对不上"的客诉。

### 3.4 无效记录治理（问题 12）

源头已由 V1.0 本地草稿改造解决（新草稿不再立刻落库），但**存量脏数据仍在**：

| 治理项 | 处理 |
|---|---|
| `status='draft' AND description=''` 的历史记录 | 列表默认过滤；另出一次性清理脚本（可先软性归档，确认无影响后物理删除） |
| `cancelled` 工单 | 不进"已完成"栏，按 3.3 归入"已取消" |
| 未来兜底 | `Update`（保存草稿）时若 `description` 为空则不落库的原则保持不变 |

## 第四章 完工单改动与留痕（问题 14、17）

### 4.1 两类改动的本质区别

问题 14 与 17 表面都是"修改已完工单据"，但性质相反。**若合并为一个接口，权限限定必然形同虚设**：

| | 14 纠错 | 17 补签 |
|---|---|---|
| 业务性质 | 改错了要修正 | 材料不齐要补齐 |
| 时限 | **完工后 N 小时内**（D4 待定值） | **不限时** |
| 权限主体 | 原接单人 + 超级管理员 | 原接单人 + 超级管理员 |
| 可改字段 | 全部（含 `quantity` / `unit_price` 金额） | **仅**签字图片 + 签字状态 |
| 接口 | 现有 `PUT /admin/orders/:id/finance` 增加时限校验 | **新增** `POST /admin/orders/:id/signature` |
| timeline 动作 | 复用 `update_finance` | 新增 `ActionSign` |

### 4.2 补签实现（问题 17）

`repair_orders.metadata` 为 `jsonb` 类型（`model.go:330`），**扩展字段无需编写 SQL 迁移**，改结构体即可，存量数据反序列化后取零值：

```go
type RepairMetadata struct {
    RepairResult    string `json:"repair_result"`
    RepairMethod    string `json:"repair_method"`
    WarrantyPeriod  string `json:"warranty_period"`
    ExtraRemark     string `json:"extra_remark"`
    RepairDuration  int    `json:"repair_duration"`
    SignatureStatus string `json:"signature_status"`  // 新增: pending / signed
}
```

`pending` = 已通知下次补签确认（对应前台选项「已通知下次补签确认」）；
`signed` = 客户已签字确认。

补签接口仅允许：① 上传/替换 `image_type='signature'` 的图片；② 将 `signature_status` 置为 `signed`。
**不接受任何金额、数量、维修内容的字段**——请求中出现这些字段应直接拒绝，而非忽略（避免调用方误以为已生效）。

### 4.3 纠错时限（问题 14）

- 时限值做成**配置项**，禁止硬编码。建议先写入 `enterprises` 表或新增轻量 `app_configs(key, value)`；在 D4 取值未定前，先以**默认 24 小时**提供配置入口。
- 超时后的处理通道：**超管解锁**。超管可突破时限，但必须写审计日志并注明原因。
- 判定基准时间：`completed_at`。

### 4.4 审计留痕

> **现状：`audit_logs` 表已建，但全库无任何 Go 代码写入**（已 grep 确认）。

问题 14 的"防止后台数据被随意修改"要真正落地，前提是先把写入机制补上：

```go
// 建议位置：internal/service/audit.go
func recordAudit(ctx context.Context, op Operator, action, targetType, targetID string,
                 before, after interface{}, ip string) error
```

调用点（5 处）：`Complete` / `UpdateFinance` / `Reopen` / `Unaudit` / `Sign`。

通知失败不得阻塞业务（沿用 `service/notifier.go` 既有约定）。

## 第六章 验收清单

### 6.1 经营范围（后端必须实跑 API，不得只读代码）

| 编号 | 用例 | 期望 |
|---|---|---|

| 编号 | 用例 | 期望 |
